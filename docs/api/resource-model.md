## 2. Ресурси предметної області (крок 2)

| Ресурс (назва в API) | Термін SRS | Опис | Джерело |
|---|---|---|---|
| `exercises` | Вправа | Елемент єдиного каталогу: прості вправи, окремі удари й комбінації в одній колекції. Ознаки: походження (`initial`/`custom`), тип, допустимі етапи, рівні, інтенсивності, акценти, характер навантаження, варіанти виконання, відеодані, позначка «застаріла» | §3, §4.3.1, REQ-F-001…004; D-05, D-06, D-07 |
| `variants` (вкладений у `exercises`, без окремих URI) | Варіант виконання | Поєднання засобу виконання, обладнання, режиму (за часом / за повтореннями) і діапазонів параметрів. Створюється й змінюється лише у складі вправи, щоб зміна вправи була атомарною (AC-F-002) | §3, §4.3.2; D-08 |
| `dictionaries` | Спільні довідники (рівень підготовки, інтенсивність, акцент тренування, обладнання, засіб виконання) | Локальні довідники значень ознак, лише для читання | §4.4 |
| `plan-generations` | Параметри формування / автоматичний підбір | Ресурс-дія: приймає параметри тренування й у разі успіху створює відкритий план. Окремо не зберігається | §2.2 п. 6–7, §4.3.3, §5; REQ-F-005…009; D-10…D-13, D-25 |
| `open-plans` | Відкритий план (новий термін глосарію) | Робоча копія плану, з якою працює користувач: результат формування або відкритий збережений план. Тут виконується ручне редагування; з неї починають тренування. Незбережений відкритий план після перезапуску відсутній; кількість відкритих планів не обмежується | §3; REQ-F-010, REQ-F-012; D-14, D-16, D-17, D-18; ADD-002 D-29 (Q-API-02), D-30 (Q-API-03) |
| `training-plans` | План тренування (збережений) | Збережений план із назвою, датою зміни, вихідними параметрами формування й етапами | §3, §4.5; REQ-F-011; D-14, D-16 |
| `items` (вкладений у `open-plans`; у `training-plans` лише читання) | Елемент плану | Використання вправи з копією назви, вибраним варіантом, етапом, позицією й параметрами | §3, §4.3.4, §4.5; REQ-F-010 |
| `current-session` (одиничний ресурс) | Поточне заняття | Тренування, для якого зафіксовано початок і яке ще не завершено й не припинено. Одночасно існує не більше одного | §3; REQ-F-012, REQ-F-013; D-17, D-18 |
| `executed-plan` (вкладений у `current-session` і `completed-trainings`) | Виконаний план | Уточнений склад і фактичні параметри виконаних вправ. У поточному занятті елементи можна змінювати й видаляти, у завершеному тренуванні — лише читати | §3; REQ-F-013; D-19, D-20 |
| `completed-trainings` | Завершене тренування | Збережений запис із датою й часом початку, локальною датою початку, копією виконаного плану та приміткою. Лише для читання після створення | §3, §4.3.5; REQ-F-013, REQ-F-014; D-20 |
| `analytics` | Аналітика (новий термін глосарію) | Обчислювані показники завершених тренувань за період. Не зберігаються | §2.2 п. 14, §8.1; REQ-F-015, REQ-F-016; D-21, D-22; ADD-002 D-29 (Q-API-02) |

**Фіксовані перелічення.** Ці значення не є ресурсами, бо їхній склад визначає SRS:

| Поле API | Термін SRS | Значення в API |
|---|---|---|
| `stage` | Етап тренування / Тренувальний блок | `warm-up` (розминка), `main` (основна частина), `cool-down` (заминка); порядок фіксований (§5.2) |
| `type` | Тип вправи | `simple` (проста вправа), `single-punch` (окремий удар), `combination` (комбінація) |
| `origin` | Походження | `initial` (початкова), `custom` (користувацька) (§4.3.1) |
| `loadCharacter` | Характер навантаження | `general-physical` (ЗФП), `special-physical` (СФП), `not-applicable` (не застосовна); одне значення на вправу, інших значень немає (ADD-002 D-34 (Q-API-10)) |
| `mode` | Режим виконання | `time` (за часом), `repetitions` (за повтореннями) (§4.3.2) |

Внутрішня реалізація (таблиці Drift/SQLite, класи Dart, провайдери Riverpod) у моделі не розкривається (SRS §8.4).

### 3.2. Свідомо відсутні операції

Ці операції не надаються. Якщо URI існує, запит з таким методом отримує `405 Method Not Allowed` із заголовком `Allow`.

| Метод і URI | Причина | Джерело |
|---|---|---|
| `DELETE /exercises/{exerciseId}` | Видалення вправ поза MVP | D-05 |
| `PUT /exercises/{exerciseId}` для початкової вправи | Початкові вправи лише для читання; повертає `403` (операція 4) | D-05 |
| `POST /training-plans` з довільним складом плану | Створення плану вручну з нуля поза MVP; план створюється лише формуванням | D-14 |
| «Зберегти як новий» (`POST /training-plans` для відкритого плану, вже пов'язаного зі збереженим) | Поза MVP; повертає `409` (операція 16) | D-16 |
| `POST`/`PUT`/`DELETE /training-plans/{planId}/items…` | Збережений план змінюється лише через відкритий план і операцію 17 | D-16 |
| `POST /current-session/executed-plan/items` | У виконаний план вправи не додаються | D-19 |
| `PUT`/`PATCH`/`DELETE /completed-trainings/{trainingId}` | Історія лише для читання | D-20 |
| Скасування формування (`DELETE /plan-generations/…`) | Скасування користувачем у MVP не передбачено | D-13 |
| Закриття відкритого плану (`DELETE /open-plans/{openPlanId}`) | Операції закриття немає; незбережений відкритий план не переживає перезапуск | ADD-002 D-30 (Q-API-03) |
| Відновлення незавершеного заняття після перезапуску | Поза MVP; після перезапуску `GET /current-session` → `404` | D-04, D-18, CON-007 |
| Відкриття, завантаження чи проксування відео | Відкриття виконує зовнішній обробник клієнта; відео не завантажуються | REQ-F-004, §2.3, §8.3 |
| Реєстрація, авторизація, профілі | Поза MVP | §2.3, §4.1 |

## 4. Деталі операцій (крок 4)

### 4.0. Загальні угоди

- **Формат.** `application/json; charset=utf-8`. Дата й час — ISO 8601 зі зміщенням (`2026-06-30T18:00:00+03:00`), локальна дата — `YYYY-MM-DD`.
- **Час.** Тривалість інтервалу, відпочинок, орієнтовний час повторення й орієнтовна тривалість — цілі секунди (§5.3, §5.4). Цільова тривалість — `hours` і `minutes` (§5.5, §8.2).
- **Посилання на довідники.** Значення ознак (рівень, інтенсивність, акцент, обладнання, засіб виконання) передаються ідентифікаторами з `GET /dictionaries/{dictionaryName}`.
- **Тексти.** API не повертає текстів для користувача. Помилки й попередження мають машинний `code` і назву поля, а клієнт будує український текст через мовний файл (REQ-NF-005, D-13).
- **Тіло помилки:**
  ```json
  { "code": "VALIDATION_FAILED",
    "details": [ { "field": "variants[0].rounds.min", "constraint": "MIN_LE_MAX" } ] }
  ```
  `details` — перелік проблемних полів і порушених правил (AC-F-002 «пояснення помилки», AC-NF-005 «помилка називає поле»).
- **Попередження** (не блокують дію, AC-F-010) — масив `warnings: [ { "code", "stage"?, "itemId"?, "attribute"? } ]` у представленні плану:
  - `DURATION_OUT_OF_TOLERANCE` — орієнтовна тривалість поза `[0,9 × D; 1,1 × D]` (D з вихідних параметрів, D-14);
  - `STAGE_EMPTY` — етап `stage` порожній;
  - `FILTER_MISMATCH` — елемент `itemId` не відповідає вихідному параметру формування `attribute` (`level`, `intensity`, `availableEquipment`, `emphasis`);
  - `STAGE_NOT_IN_EXERCISE` — інформаційне: етап елемента не зазначено у вправі (REQ-F-010, «якщо воно відображається»; клієнт може його не показувати).
- **Спільні коди стану:**

  | Код | Коли |
  |---|---|
  | `400 Bad Request` | `code: BAD_REQUEST` — некоректний JSON, неправильний тип поля, неправильний формат дати |
  | `404 Not Found` | `code: NOT_FOUND` — ресурс із path-ідентифікатором не існує; для відсутнього поточного заняття — `code: NO_CURRENT_SESSION` |
  | `405 Method Not Allowed` | Метод не надається для ресурсу (розділ 3.2) |
  | `409 Conflict` | Дія суперечить поточному стану (наприклад, уже є поточне заняття) |
  | `422 Unprocessable Content` | Запит синтаксично коректний, але порушує правила предметної області |
  | `500 Internal Server Error` | Технічна помилка; `code: STORAGE_WRITE_FAILED` — запис не завершено, попередній стан збережено (REQ-NF-003) |

  Успіх (`200`/`201`/`204`) для записувальних операцій повертається лише після повного завершення запису (AC-NF-003).

- **Представлення вправи (`Exercise`):** `id`, `name`, `description`, `origin`, `type`, `allowedStages[]`, `allowedLevels[]`, `allowedIntensities[]`, `emphases[]`, `loadCharacter`, `variants[]`, `videoUrl` (string|null), `videoAuthorName` (string|null), `authorPageUrl` (string|null), `deprecated` (boolean).
- **Представлення варіанта (`Variant`):** `id` (стабільний у межах вправи, зберігається під час редагування вправи, ADD-002 D-33 (Q-API-08)), `executionMeans`, `equipment[]`, `mode`, далі діапазони `{ min, max, recommended }` за D-08:
  - `mode = time`: `rounds`, `intervalSeconds`, `restSeconds`;
  - `mode = repetitions`: `sets`, `repetitions`, `restSeconds`, а також фіксований `repetitionTimeSeconds` (`e`).
- **Представлення елемента плану (`PlanItem`):** `id`, `exerciseId`, `exerciseName` (копія), `variant` (копія `Variant` на момент включення, §4.5), `stage`, `position` (з 0 у межах етапу), `parameters`, `estimatedDurationSeconds`.
  - `parameters` для `time`: `rounds`, `intervalSeconds`, `restSeconds`;
  - `parameters` для `repetitions`: `sets`, `repetitions`, `restSeconds`, `repetitionTimeSeconds` (лише читання, D-08).
- **Представлення плану (`Plan`):** `name` (string|null; `null` у сформованого незбереженого плану, ADD-002 D-32 (Q-API-05)), `generationParameters`, `targetDurationSeconds` (`D`), `durationTolerance { minSeconds, maxSeconds }`, `stages: [ { stage, items: PlanItem[] } ]` (завжди три етапи в порядку `warm-up`, `main`, `cool-down`), `estimatedDurationSeconds`, `warnings[]`.
  - `generationParameters`: `targetDuration { hours, minutes }`, `level`, `emphasis`, `availableEquipment[]`, `intensity` — п'ять параметрів REQ-F-005. «Режим» у D-14 не є окремим параметром (ADD-002 D-31 (Q-API-04)).
  - `OpenPlan` = `Plan` + `id`, `sourcePlanId` (null для ще не збереженого результату формування).
  - `SavedPlan` = `Plan` + `id`, `modifiedAt`.

### 4.6. `POST /plan-generations` — формування плану

- **Трасування:** REQ-F-005…009, AC-F-005…009; BDD-006, BDD-007, BDD-010, BDD-011, BDD-012; D-06, D-10, D-11, D-12, D-13, D-14, D-25; ADD-002 D-30 (Q-API-03), D-31 (Q-API-04), D-32 (Q-API-05).
- **Request body:** `targetDuration { hours, minutes }`, `level`, `emphasis`, `availableEquipment[]`, `intensity`. Ці п'ять параметрів зберігаються в плані як `generationParameters`.
  Порожній `availableEquipment` дозволений: підбираються лише варіанти без обладнання (AC-F-005).
- **Відповідь `201`:** `OpenPlan` з `sourcePlanId: null` і `name: null`; `Location: /open-plans/{openPlanId}`. Поточне заняття формуванню не заважає. Гарантії успішної відповіді:
  - три непорожні етапи у фіксованому порядку (AC-F-006);
  - кожен варіант задовольняє правила §5.1 і не застарілий (D-06);
  - кожен варіант включено не більше одного разу (AC-F-006);
  - усі параметри в межах `[min; max]` варіанта, починаючи з рекомендованих (D-10);
  - `0,9 × D ≤ estimatedDurationSeconds ≤ 1,1 × D` за точними секундами (AC-F-008).

  План автоматично **не зберігається** (D-17). Повторне формування з тими самими параметрами може дати інший допустимий план (D-11).
- **Коди стану** (три неуспішні результати формування розрізняються кодом стану і `code`, AC-F-009 п. 5):

  | Код | `code` | Коли | Що повертається |
  |---|---|---|---|
  | `201` | — | Знайдено допустимий план | `OpenPlan` |
  | `400` | `BAD_REQUEST` | Некоректний JSON або тип поля | Тіло помилки |
  | `422` | `VALIDATION_FAILED` | Параметри не пройшли перевірку **до початку пошуку**: `hours < 0`; `minutes` поза `0…59`; `hours × 3600 + minutes × 60 = 0`; відсутнє обов'язкове поле; невідоме значення довідника (AC-F-005, BDD-006) | `details` з полями |
  | `422` | `PLAN_GENERATION_IMPOSSIBLE` | **Доведена неможливість**: допустимого плану не існує за цими параметрами й каталогом. Причини в необов'язковому `reasons[]`: `NO_CANDIDATES_FOR_STAGE` (+`stage`) — немає придатних вправ для обов'язкового етапу (AC-F-009 п. 1, BDD-011); `MAX_VOLUME_BELOW_LOWER_BOUND` — навіть максимальний обсяг < `0,9 × D` (AC-F-009 п. 2, BDD-012); `MIN_VOLUME_ABOVE_UPPER_BOUND` — навіть мінімальний обсяг > `1,1 × D` (D-10) | Тіло помилки; клієнт показує текст D-13 «За заданими параметрами план сформувати неможливо…» |
  | `500` | `GENERATION_FAILED` | Технічна помилка генератора, не пов'язана з лімітом | Тіло помилки |
  | `503` | `GENERATION_SEARCH_LIMIT_REACHED` | **Технічний ліміт пошуку**: під час перевірки минуло ≥ 3,000 с від початку пошуку (D-13, D-25). Це **не доказ** відсутності плану (§5.7). Повторний запит допустимий | `{ code, limitSeconds: 3 }`; клієнт показує текст D-13 «Не вдалося знайти план за відведений час. Спробуйте ще раз…» |

  У жодному неуспішному випадку відкритий план не створюється й неповний результат не повертається (AC-F-009 п. 3, §5.7).

- **Коди стану:** `200`; `404` — плану чи елемента немає.

### 4.14. `GET /training-plans` — перелік збережених планів

- **Трасування:** REQ-F-011; D-16.
- **Query:** немає.
- **Відповідь `200`:** `{ "items": [ { id, name, modifiedAt } ] }`, упорядковано за `modifiedAt` від новіших до старіших (D-16). Порожній перелік — `items: []`.
- **Коди стану:** `200`.

### 4.15. `GET /training-plans/{planId}` — збережений план

- **Трасування:** REQ-F-011, AC-F-011; BDD-015; D-06, D-16.
- **Path:** `planId`.
- **Відповідь `200`:** `SavedPlan` — ті самі етапи, порядок, варіанти й параметри, що були збережені (AC-F-011); зміни каталогу план не переписують.
- **Коди стану:** `200`; `404`.

### 4.16. `POST /training-plans` — перше збереження сформованого плану

- **Трасування:** REQ-F-011, REQ-NF-002, REQ-NF-003, AC-F-011, AC-NF-003; BDD-014, BDD-023, BDD-033; D-14, D-16; ADD-002 D-32 (Q-API-05).
- **Request body:** `openPlanId`. Склад плану береться з відкритого плану; довільний склад у тілі не приймається (D-14).
- **Відповідь `201`:** `SavedPlan` з `warnings[]` (попередження не блокують збереження, BDD-014); `Location: /training-plans/{planId}`. Порожня назва або `null` замінюється назвою за замовчуванням «План від ДД.ММ.РРРР ГГ:ХХ», де дата й час — момент збереження (D-16, ADD-002 D-32 (Q-API-05)). Після успіху `sourcePlanId` відкритого плану дорівнює новому `planId`.
- **Коди стану:**
  - `201` — план збережено повністю;
  - `400` — некоректне тіло;
  - `409 OPEN_PLAN_ALREADY_SAVED` — відкритий план уже пов'язаний зі збереженим. Його можна лише перезаписати операцією 4.17; «Зберегти як новий» поза MVP (D-16);
  - `422 OPEN_PLAN_NOT_FOUND` — відкритого плану немає;
  - `422 PLAN_EMPTY` — у плані немає жодного елемента (AC-F-011, BDD-033);
  - `500 STORAGE_WRITE_FAILED` — запис не завершено, план не створено (AC-NF-003).

### 4.17. `PUT /training-plans/{planId}` — збереження з перезаписом

- **Трасування:** REQ-F-011, REQ-NF-003, AC-F-011, AC-NF-003; BDD-014, BDD-033; D-16; ADD-002 D-32 (Q-API-05).
- **Path:** `planId`.
- **Request body:** `openPlanId`. У відкритого плану `sourcePlanId` має дорівнювати `planId`.
- **Відповідь `200`:** `SavedPlan` з оновленими `modifiedAt` і `warnings[]`. Порожня назва замінюється назвою за замовчуванням із датою й часом моменту збереження (D-16, ADD-002 D-32 (Q-API-05)).
- **Коди стану:**
  - `200` — план перезаписано повністю;
  - `400` — некоректне тіло;
  - `404` — збереженого плану `planId` немає, зокрема якщо його видалили після відкриття. Зберегти такий відкритий план як новий неможливо: «Зберегти як новий» поза MVP (D-16);
  - `409 OPEN_PLAN_SOURCE_MISMATCH` — відкритий план не походить із `planId`;
  - `422 OPEN_PLAN_NOT_FOUND`, `422 PLAN_EMPTY` — як в операції 4.16;
  - `500 STORAGE_WRITE_FAILED` — діє попередній стан збереженого плану (AC-NF-003).

### 4.18. `DELETE /training-plans/{planId}` — видалення плану

- **Трасування:** REQ-F-011; D-16.
- **Path:** `planId`. Підтвердження показує лише клієнт до запиту; ознаки підтвердження в API немає.
- **Відповідь `204`:** без тіла. Історія й поточне заняття не змінюються, бо містять власні копії (§4.5).
- **Коди стану:** `204`; `404`; `500 STORAGE_WRITE_FAILED`.

### 4.19. `POST /current-session` — початок тренування

- **Трасування:** REQ-F-012, AC-F-012; BDD-016, BDD-025, BDD-026; D-17, D-18.
- **Request body:** `openPlanId` — будь-який відкритий план, збережений чи ні (D-17).
- **Відповідь `201`:** `{ startedAt, localStartDate, executedPlan: { stages: [ { stage, items: PlanItem[] } ] } }`; `Location: /current-session`.
  - `startedAt` і `localStartDate` фіксуються в момент обробки запиту (REQ-F-012, AC-F-015);
  - `executedPlan` — робоча копія відкритого плану (AC-F-012);
  - план автоматично не зберігається (D-17); заняття не входить до історії й аналітики (AC-F-012).
- **Коди стану:**
  - `201` — заняття створено;
  - `400` — некоректне тіло;
  - `409 SESSION_ALREADY_ACTIVE` — поточне заняття вже існує. Друге не створюється, дані наявного не змінюються (AC-F-012 п. 4, BDD-025). Це єдине блокування, пов'язане з поточним заняттям, яке забезпечує API; заборону відкривати інше тренування забезпечує інтерфейс (AC-F-012 п. 5);
  - `422 OPEN_PLAN_NOT_FOUND` — відкритого плану немає;
  - `422 PLAN_EMPTY` — відкритий план порожній (REQ-F-012).

### 4.20. `GET /current-session` — поточне заняття

- **Трасування:** REQ-F-012; D-18.
- **Відповідь `200`:** як в операції 4.19.
- **Коди стану:** `200`; `404 NO_CURRENT_SESSION` — поточного заняття немає, зокрема після перезапуску чи вивантаження застосунку (D-18).

### 4.21. `PATCH /current-session/executed-plan/items/{itemId}` — уточнення фактичних параметрів

- **Трасування:** REQ-F-013, AC-F-013; BDD-016; D-19.
- **Path:** `itemId`.
- **Request body:** часткові фактичні `parameters`: для `time` — `rounds`, `intervalSeconds`, `restSeconds`; для `repetitions` — `sets`, `repetitions`, `restSeconds`.
- **Відповідь `200`:** поточне заняття (як в операції 4.19).
- **Коди стану:**
  - `200` — значення прийнято. Межі варіанта `[min; max]` **не застосовуються**: значення понад максимум допустиме (D-19);
  - `400` — некоректне тіло;
  - `404 NO_CURRENT_SESSION` — поточного заняття немає; `404 NOT_FOUND` — елемента немає;
  - `422 VALIDATION_FAILED` — кількість, повторення чи інтервал не є цілим ≥ 1, відпочинок не є цілим ≥ 0, поле не відповідає `mode`, передано поле поза переліком D-19 (зокрема `stage`, `position`, `repetitionTimeSeconds`).

### 4.22. `DELETE /current-session/executed-plan/items/{itemId}` — видалення виконаної вправи

- **Трасування:** REQ-F-013, AC-F-013; BDD-028; D-19.
- **Path:** `itemId`.
- **Відповідь `200`:** поточне заняття. Повне спорожнення виконаного плану допустиме (BDD-028).
- **Коди стану:** `200`; `404 NO_CURRENT_SESSION` — заняття немає; `404 NOT_FOUND` — елемента немає.

### 4.23. `DELETE /current-session` — припинення без збереження

- **Трасування:** REQ-F-013, AC-F-013; BDD-026, BDD-027, BDD-028.
- **Передумова:** клієнт попередив про втрату даних і отримав підтвердження. Якщо підтвердження відхилено, запит не надсилається й заняття не змінюється (BDD-027). Ознаки підтвердження в API немає.
- **Відповідь `204`:** заняття закрито, незбережені зміни відкинуто; запис історії не створюється; аналітика й збережений план не змінюються; почати інше тренування знову можна (AC-F-013). Дозволено й для порожнього виконаного плану.
- **Коди стану:** `204`; `404 NO_CURRENT_SESSION`.

### 4.24. `POST /completed-trainings` — завершення зі збереженням

- **Трасування:** REQ-F-013, REQ-NF-002, REQ-NF-003, AC-F-013, AC-NF-003; BDD-016, BDD-021, BDD-028, BDD-029.
- **Request body:** `note?` (рядок; відсутній або `null` — порожнє значення). Завершується поточне заняття; ключа ідемпотентності немає.
- **Відповідь `201`:** `CompletedTraining` (див. операцію 4.26); `Location: /completed-trainings/{trainingId}`. Поточне заняття закривається.
  Завершення не залежить від часу, що минув від початку, і не позначає тренування невиконаним через перевищення орієнтовної тривалості (BDD-029).
- **Коди стану:**
  - `201` — запис створено, заняття більше не поточне;
  - `400` — некоректне тіло;
  - `409 NO_CURRENT_SESSION` — поточного заняття немає. Це стосується й повторного запиту після успішного завершення: заняття вже не поточне, тому дубліката немає (AC-F-013, BDD-016);
  - `422 EXECUTED_PLAN_EMPTY` — виконаний план порожній. Запис не створюється, заняття залишається поточним (AC-F-013, BDD-028);
  - `500 STORAGE_WRITE_FAILED` — запис не завершено: часткового запису немає, заняття залишається поточним, успіх не повідомляється (AC-NF-003, BDD-021).

### 4.25. `GET /completed-trainings` — історія

- **Трасування:** REQ-F-014, AC-F-014; BDD-020; D-20.
- **Query:** немає.
- **Відповідь `200`:** `{ "items": [ { id, startedAt } ] }`, упорядковано за `startedAt` від новіших до старіших (AC-F-014). Порожня історія — `items: []`.
- **Коди стану:** `200`.

### 4.26. `GET /completed-trainings/{trainingId}` — деталі тренування

- **Трасування:** REQ-F-014, AC-F-014; BDD-016, BDD-017; D-06, D-20.
- **Path:** `trainingId`.
- **Відповідь `200`:** `CompletedTraining`: `id`, `startedAt`, `localStartDate`, `executedPlan { stages: [ { stage, items: PlanItem[] } ] }` (копії назв, варіантів і фактичних параметрів), `note` (string|null). Зміни каталогу запис не змінюють (BDD-017).
- **Коди стану:** `200`; `404`.

### 4.27. `GET /analytics` — показники за період

- **Трасування:** REQ-F-015, REQ-F-016, AC-F-015, AC-F-016; BDD-018, BDD-019, BDD-020, BDD-026, BDD-030; D-21, D-22; ADD-002 D-35 (Q-API-11).
- **Query:** `from?`, `to?` (`YYYY-MM-DD`, включно). Задаються обидва або жоден (ADD-002 D-35 (Q-API-11)). Якщо обидва відсутні — `to` = сьогодні, `from` = `to − 29 днів` (AC-F-015). «Сьогодні» — локальна дата пристрою.
- **Відповідь `200`:**
  - `period { from, to }`;
  - `completedTrainingCount` — кількість завершених тренувань із `localStartDate` у періоді;
  - `dailyCounts: [ { date, count } ]` — **кожен** день періоду, зокрема з `count: 0` (D-22); сума `count` дорівнює `completedTrainingCount`;
  - `exerciseFrequencies: [ { exerciseId, exerciseName, trainingCount } ]` — групування за стабільним `exerciseId`. `trainingCount` — кількість тренувань, у яких вправа трапляється хоча б раз; кілька включень чи різні варіанти в одному тренуванні рахуються один раз. `exerciseName` береться з копії в найновішому тренуванні періоду (AC-F-016, D-22). Порядок елементів контрактом не визначається.

  Поточне заняття не враховується (BDD-019). За відсутності даних — `completedTrainingCount: 0`, `exerciseFrequencies: []` (BDD-020).
- **Коди стану:**
  - `200` — період коректний, зокрема без даних;
  - `400` — неправильний формат дати;
  - `422 INVALID_PERIOD` — `from` пізніше за `to` (AC-F-015, BDD-030) або задано лише один із параметрів `from`/`to` (ADD-002 D-35 (Q-API-11));
  - `422 END_DATE_IN_FUTURE` — `to` пізніше за локальну дату пристрою (D-21). Довжина періоду не обмежена (D-21).
