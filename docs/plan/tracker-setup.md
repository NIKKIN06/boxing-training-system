# Налаштування системи багтрекінгу

**Проєкт:** Інформаційна система планування та формування тренувань з боксу
**Джерело планування:** SRS v1.0 (`spec/srs.md`, коміт `533ee59`)
**Дата налаштування:** 16.10.2026
**Налаштував:** Наумов Нікіта Сергійович

## 1. Обраний трекер

**GitHub Issues + GitHub Projects**

- Репозиторій: https://github.com/NIKKIN06/boxing-training-system
- Project: `Boxing Training System — SDD Implementation Plan` — <https://github.com/users/NIKKIN06/projects/3>

Причини вибору:

1. Тікети зберігаються поряд з артефактами SDD. Issue може посилатися на файли `spec/`, коміти й інші issues того самого репозиторію без зовнішніх інтеграцій.
2. Система підтримує все, що вимагає п. 1 ЛР-3 (див. таблицю нижче).
3. GitHub CLI (`gh`) дозволяє кодинговому агенту готувати команди створення тікетів, які виконуються лише після підтвердження людиною.
4. Project публічний, тому викладач може переглянути план без запрошення.

| Вимога п. 1 ЛР-3 | Засіб GitHub |
| --- | --- |
| Створення задач | Issues |
| Статуси | Поле `Status` у Project |
| Виконавці | Поле `Executor` (агент / людина / спільно) і `Assignees` |
| Залежності | Зв'язки «blocked by» між issues, sub-issues |
| Історія змін | Timeline кожного issue, історія Project |

## 2. Робочий процес (статуси)

| Статус | Значення | Хто переводить |
| --- | --- | --- |
| `Todo` | Невиконана робота | Автоматично при додаванні до Project |
| `In progress` | Активна робота | Виконавець тікета |
| `In review` | Перевірювана робота: людина переглядає результат агента | Виконавець після завершення роботи |
| `Done` | Завершена і прийнята робота | Людина після перевірки; автоматично при закритті issue |

Окремий статус «Blocked» не вводився. Блокування відображаються зв'язками «blocked by», а мінімальний набір із чотирьох статусів достатньо розрізняє невиконану, активну, перевірювану й завершену роботу.

Тікети типу Gate переводить у `Done` і закриває лише людина, після запису рішення в `logs/`.

## 3. Типи тікетів

Типи задано мітками. Вбудовані issue types GitHub доступні лише для репозиторіїв організацій, а цей репозиторій особистий.

| Мітка | Роль у SDD-циклі | Переважний виконавець |
| --- | --- | --- |
| `type:Specification` | Робота зі специфікацією та її уточнення | Спільно |
| `type:Addendum` | Нова або змінена вимога, виявлена після затвердження SRS | Спільно |
| `type:Test` | Тести, побудовані з критеріїв прийняття та BDD-сценаріїв | Агент |
| `type:Feature` | Реалізація функціональності за вимогою | Агент |
| `type:Verification` | Перевірка відповідності реалізації специфікації | Спільно |
| `type:Validation` | Перевірка відповідності продукту задуму | Людина |
| `type:Documentation` | Проєктна та користувацька документація | Агент |
| `type:Gate` | Дозвіл або заборона переходу до наступного етапу; не створює код чи тести | Людина |

Нова функціональність не додається тікетом `type:Feature` напряму. Вона оформлюється через `type:Addendum` після рішення REVISE.

## 4. Поля Project

| Поле | Тип | Значення | Призначення |
| --- | --- | --- | --- |
| `Status` | Single select | `Todo`, `In progress`, `In review`, `Done` | Робочий процес |
| `Executor` | Single select | `Agent`, `Human`, `Joint` | Розподіл ролей людини й агента |
| `Stage` | Single select | Узгоджуються з етапами `docs/plan/plan.md` | Належність тікета до етапу плану |
| `Start date` | Date | — | Календарний план, вигляд Roadmap |
| `Target date` | Date | — | Календарний план, вигляд Roadmap |
| `Estimate (h)` | Number | — | Орієнтовна тривалість |
| `Sub-issues progress` | Системне | — | Частка завершених sub-issues |

Поле названо `Executor`, а не `Assignee`, щоб не плутати з вбудованим полем `Assignees`, яке містить облікові записи GitHub. Агент не має облікового запису, тому роль виконавця задається окремим полем.

## 7. Дефолтні мітки GitHub

| Мітка | Рішення | Причина |
| --- | --- | --- |
| `enhancement` | Архівовано | Суперечить SDD: нова функціональність оформлюється через `type:Addendum` |
| `documentation` | Архівовано | Дублює `type:Documentation` |
| `good first issue` | Архівовано | Призначена для зовнішніх учасників, яких у проєкті немає |
| `help wanted` | Архівовано | Призначена для зовнішніх учасників, яких у проєкті немає |
| `accessibility` | Архівовано | У SRS немає вимог до доступності |
| `duplicate` | Залишено | Закриття дублікатів, створених під час роботи з `gh` |
| `invalid` | Залишено | Закриття тікетів без джерела в SRS, вилучених під час перевірки |
| `question` | Залишено | Питання до специфікації, виявлені під час декомпозиції |
| `bug` | Залишено | Дефекти на етапі реалізації |
| `wontfix` | Залишено | Тікети, від яких свідомо відмовились |

Мітки архівовано, а не видалено, щоб за потреби їх можна було повернути.

## 8. Правила використання

1. Кожен тікет містить розділ «Джерело» з ID вимог (REQ-F-xxx, REQ-NF-xxx), критеріїв (AC-...) або сценаріїв (BDD-...).
2. Тікет без джерела в SRS вилучається або повертається на уточнення вимог.
3. Агент використовує лише мітки `type:*`; мітки `duplicate`, `invalid`, `question`, `bug` і `wontfix` — лише за вказівкою людини. Нові мітки агент не створює.
4. Тікети `type:Feature` блоковані відповідними `type:Test` і `type:Gate`. Виняток (рішення людини від 17.10.2026): тікет каркаса Flutter-проєкту (T-10 у `docs/plan/decomposition-draft.md`) не має попереднього `type:Test`, бо тести неможливо запустити без проєкту. Критерій його готовності: проєкт збирається, а порожній димовий тест проходить.
5. Тікети `type:Gate` закриває лише людина після запису рішення в `logs/`.
