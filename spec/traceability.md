# Матриця простежуваності

Стан на 14.11.2026. Пов'язана специфікація: `spec/srs.md`, версія 1.2 (внесено ADD-001, ADD-002 і ADD-003). Позначки `D-xx` у колонці «Критерій» вказують рішення адендумів, якими доповнено критерій.

Матриця встановлює зв'язки: «вимога → критерій прийняття → BDD або інший спосіб перевірки → тікет → тест → код».

BDD містяться в `spec/acceptance.feature`.

Пов'язаний контракт API — `spec/openapi.yaml` 1.1.0 (затверджено на API-GATE, `logs/api-gate.md`; доповнено ADD-003 після SPEC-ADDENDUM-GATE, `logs/spec-addendum-gate.md`); детальна простежуваність — `docs/api/req-api-traceability.md`.

Колонки «Тест» і «Код» заповнено 14.11.2026 на кроці 8 ЛР-5 за правилом ПР-02 (`docs/plan/decomposition.md`) для обсягу ЛР-5 — REST API (рішення людини 12.11.2026, `logs/agent-session-lab5.md`, етап 1):

- «Тест» — файли тестів відносно `tests/test/`; у дужках — кількість тестів файлу, пов'язаних із вимогою, і ID з назв цих тестів (AC, BDD, D-xx; POS / NEG — лише якщо інших ID немає). Склад згенеровано скриптом за JSON-звітом останнього повного прогону `logs/app/control-green-t69-refactor-20261114.jsonl` (346 тестів, 346 пройдено). Вимогу визначено за номером AC, тегами BDD у `spec/acceptance.feature` і колонкою REQ-ID POS / NEG у `docs/api/scenarios.md`.
- «Код» — файли реалізації за компонентами (маршрути, сервіси, репозиторії й сховища, моделі й валідація, конфігурація, логування); шляхи відносно `src/lib/src/`, крім `bin/…` і `assets/…` (відносно `src/`).
- «Поза обсягом ЛР-5» — клієнтські частини (Flutter / Android) і перевірки на погодженому каталозі; відповідні тікети лишаються відкритими.

## Межі поточної матриці

Для REQ-NF-005 і REQ-NF-006 окремі BDD не створюються: їх перевірка передбачає інспекцію коду, ресурсів або артефактів процесу. REQ-NF-004 перевіряється BDD-050 (очищення посилань) та інспекцією мережевої активності (D-02).

Обмеження CON-001…CON-008 (D-24) перевіряються інспекцією; критеріїв прийняття й BDD вони не мають. Колонку «Тікет» для рядків CON заповнено 14.11.2026 на кроці 8 ЛР-5 (V-001, завдання T-09) за таблицею покриття `docs/plan/decomposition.md` (рядки CON-001…CON-008); номери issues взято з виводу `gh issue list --state all --limit 200 --json number,title`. Колонки «Тест» і «Код» для рядків CON не заповнюються: результати інспекції — `logs/verification-lab5.md`, розділ 2.2.

Для D-28, D-29 і D-31 окремі BDD не створюються: ці рішення визначають статус артефакту, терміни глосарію та склад даних, які перевіряються сценаріями D-30 і D-32 та інспекцією документів (ADD-002, 3.4).

BDD без автоматизованого тесту в обсязі ЛР-5: BDD-005, BDD-027, BDD-031, BDD-050 — клієнтські сценарії, позначені в колонці «Тест» як «поза обсягом ЛР-5».

Колонка «Тест» не перелічує `contract/operation_coverage_test.dart` у рядках REQ-F: цей тест (AC-NF-006) викликає кожну з 27 операцій за першим POS-сценарієм і перевіряє лише оголошений статус, тому його віднесено до REQ-NF-006.

Колонку «Документація» заповнюють тікети `Documentation` (ПР-02); у ЛР-5 її не заповнено.

Додаткові способи перевірки є планом перевірок; результати їх виконання для обсягу ЛР-5 наведено в `logs/verification-lab5.md`.
