# ADD-002. Уточнення SRS v1.0 і ADD-001 за результатами проєктування REST API

| Поле | Значення |
|---|---|
| Статус | **Затверджено людиною 26.10.2026**. Зміни до `spec/srs.md`, `spec/acceptance.feature`, `spec/traceability.md` ще **не внесено** |
| Базова специфікація | SRS v1.0 (`spec/srs.md`) з урахуванням ADD-001 |
| Дата | 24.10.2026 |
| Підготував | Кодинговий агент (Claude Code) за рішеннями людини |
| Джерело питань | `docs/api/resource-model.md`, розділ 5 (Q-API-01…15) |

## 1. Причина зміни

Під час проєктування REST API (ЛР-4) виявлено неоднозначності та прогалини SRS v1.0 і ADD-001 (`docs/api/resource-model.md`, розділ 5). Людина ухвалила рішення щодо кожного з них. Рішення, що змінюють або уточнюють специфікацію, оформлено цим адендумом відповідно до SRS §1.

Позначки виду (як в ADD-001):

- **[У]** — уточнення: поведінка, що випливала з SRS або ADD-001 неоднозначно, тепер визначена однозначно;
- **[Н]** — нова поведінка або нові дані, яких у SRS v1.0 і ADD-001 не було.

Рішення щодо Q-API-06, Q-API-07, Q-API-09, Q-API-11 (б, в), Q-API-12…15 оформлено в контракті API без зміни специфікації й до адендуму не входять (див. `docs/api/resource-model.md`, розділ 5).

## 2. Рішення

Формат: **ID рішення** · питання з `docs/api/resource-model.md` · вимоги · вид.

### Межі та статус API

**D-28** · Q-API-01 · REQ-NF-001, REQ-NF-004, SRS §2.3 · **[У]**
OpenAPI-специфікація — проєктний контракт операцій системи (API-first). У MVP не розгортається як мережевий сервер; mock запускається лише локально для перевірки контракту. §2.3, REQ-NF-001, REQ-NF-004 не змінюються.

### Глосарій

**D-29** · Q-API-02 · SRS §3; REQ-F-015, REQ-F-016; D-16, D-17 · **[У]**
До глосарію додаються терміни «Відкритий план» і «Аналітика».

Визначення для SRS §3:

| Термін | Визначення |
|---|---|
| Відкритий план | Робоча копія плану тренування, з якою працює користувач: ще не збережений план або відкритий збережений план. Збереження відкритого збереженого плану перезаписує його. Тренування можна почати з будь-якого відкритого плану, збереженого чи ні; початок тренування не зберігає план автоматично. Незбережений відкритий план не зберігається після перезапуску застосунку |
| Аналітика | Показники завершених тренувань за останні 30 календарних днів за замовчуванням або за вибраним діапазоном дат: кількість завершених тренувань, кількість тренувань за днями та частота використання вправ. Незавершені заняття не враховуються |

Джерела визначень: «Відкритий план» — D-16, D-17, D-30 (Q-API-03); «Аналітика» — REQ-F-015, REQ-F-016.

### План тренування

**D-30** · Q-API-03 · REQ-F-010, REQ-F-011, REQ-F-012; D-16, D-17, D-18 · **[У]**
Відкритий план — робоча копія. Незбережений відкритий план не переживає перезапуск (як D-18). Кількість відкритих планів контрактом не обмежується. Операції закриття немає.

**D-31** · Q-API-04 · REQ-F-005, REQ-F-011; D-14 · **[У]**
«Режим» у D-14 не є окремим параметром; вихідні параметри формування — п'ять параметрів REQ-F-005.

**D-32** · Q-API-05 · REQ-F-011, AC-F-011; D-16 · **[У]**
Сформований незбережений план не має назви. Дата й час у назві за замовчуванням — момент збереження.

У контракті API: поле name = null.

### Каталог і вправи

**D-33** · Q-API-08 · REQ-F-002, REQ-F-006, REQ-F-010; SRS §4.3.2, §5.2 · **[Н]**
Варіант виконання має стабільний ідентифікатор у межах вправи, що зберігається під час редагування вправи.

**D-34** · Q-API-10 · REQ-F-003, AC-F-003; SRS §3, §4.3.1; D-09 · **[У]**
Характер навантаження має одне значення з переліку: ЗФП, СФП, не застосовна. Правило «не застосовна» з D-09 стосується лише цієї ознаки.

У контракті API: loadCharacter — general-physical, special-physical, not-applicable.

### Аналітика

**D-35** · Q-API-11 (а) · REQ-F-015, AC-F-015; D-21 · **[У]**
Початкова й кінцева дати періоду аналітики задаються обидві або жодна; якщо задано лише одну, діапазон відхиляється.

У контракті API: 422 INVALID_PERIOD.

| Вид | Рішення |
|---|---|
| [У] | D-28, D-29, D-30, D-31, D-32, D-34, D-35 |
| [Н] | D-33 |

## 3. Вплив на артефакти специфікації

Нижче перелічено, що доведеться змінити чи додати в SRS v1.0 з урахуванням ADD-001. Формулювання агент готує окремим diff і застосовує лише за прямою вказівкою людини. Частина змін уточнює положення ADD-001, які в `spec/srs.md` ще не внесено. Їх застосовують разом з ADD-001 або після нього.

### 3.1. SRS: розділи та вимоги (REQ)

| Елемент | Зміна | Рішення |
|---|---|---|
| §2.3, §4.2 | Текст не змінюється. За потреби — примітка, що OpenAPI-специфікація є проєктним контрактом і в MVP не розгортається як мережевий сервер | D-28 |
| §3 (глосарій) | Додати терміни «Відкритий план» і «Аналітика» (визначення в D-29). У терміні «Характер навантаження» замінити «зокрема ЗФП або СФП» на закритий перелік: ЗФП, СФП, не застосовна; одне значення на вправу | D-29, D-34 |
| §4.3 (новий підрозділ «План тренування», ADD-001) | Вихідні параметри формування — п'ять параметрів REQ-F-005, без окремого «режиму» (уточнює рядок ADD-001 §3.1 «фільтри, `D`, режим»). Назва: у сформованого незбереженого плану відсутня; дата й час у назві за замовчуванням — момент збереження. Відкритий план — робоча копія; незбережений не переживає перезапуск; кількість не обмежується; закриття не передбачено | D-30, D-31, D-32 |
| §4.3.1 | Характер навантаження — одне значення з переліку ЗФП / СФП / не застосовна | D-34 |
| §4.3.2 | Додати стабільний ідентифікатор варіанта в межах вправи, що зберігається під час редагування вправи | D-33 |
| §5.2 | Правило «один варіант не більше одного разу» спирається на ідентифікатор варіанта (D-33) | D-33 |
| §8.1 | Область «План» — робота з відкритим планом (термін D-29); область «Аналітика» — термін D-29 | D-29, D-30 |
| §10 | За потреби — згадати OpenAPI-специфікацію серед пов'язаних артефактів як проєктний контракт | D-28 |
| REQ-F-002 | Редагування вправи зберігає ідентифікатори наявних варіантів | D-33 |
| REQ-F-003 | Значення «не застосовна» (D-09) стосується лише ознаки «характер навантаження» | D-34 |
| REQ-F-011 | Назва: відсутня в незбереженого сформованого плану; за замовчуванням — з датою й часом збереження. Вихідні параметри — п'ять параметрів REQ-F-005 | D-31, D-32 |
| REQ-F-012 | Тренування починають з відкритого плану (термін D-29); незбережений відкритий план не переживає перезапуск | D-29, D-30 |
| REQ-F-015 | Початкова й кінцева дати задаються обидві або жодна | D-35 |
| REQ-NF-001, REQ-NF-004 | Без змін тексту; D-28 підтверджує, що API не розгортається як мережевий сервер | D-28 |

Нових REQ-ID не додається.

Без змін: REQ-F-001, REQ-F-004, REQ-F-005, REQ-F-007, REQ-F-008, REQ-F-009, REQ-F-013, REQ-F-014, REQ-F-016, REQ-NF-002, REQ-NF-003, REQ-NF-005, REQ-NF-006.

## 4. Порядок застосування

1. Людина переглядає ADD-002 і затверджує його або повертає на доопрацювання.
2. Після затвердження агент готує diff для `spec/srs.md`, `spec/acceptance.feature` і `spec/traceability.md` разом із змінами ADD-001 або після них і застосовує його лише за прямою вказівкою людини.
3. Людина перевіряє узгодженість специфікації на контрольній точці й записує рішення в `logs/spec-gate.md`.
4. До затвердження ADD-002 рішення D-28…D-35 у `docs/api/resource-model.md` залишаються частиною чернетки контракту.
